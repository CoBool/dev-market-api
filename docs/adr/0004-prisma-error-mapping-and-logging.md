# 0004. Prisma 에러: 4xx는 조용히, 5xx는 반드시 기록

- 상태: 승인됨
- 날짜: 2026-10-05

## 배경
`PrismaExceptionFilter`의 default 분기가 500을 응답하면서 **로그를 남기지 않았다.**
필터가 예외를 잡으면 Nest 기본 처리기의 로깅도 일어나지 않아, 원인을 추적할 수 없었다.

## 결정

| Prisma 코드 | 의미 | 응답 | 로그 |
|---|---|---|---|
| P2002 | unique 위반 | 409 | 없음 |
| P2025 | 대상 없음 | 404 | 없음 |
| P2003 | 외래 키 위반 | 409 | 없음 |
| 그 외 `PrismaClientKnownRequestError` | 예상 못 한 DB 에러 | 500 | `Logger.error` (코드 + 스택) |

- `PrismaClientValidationError`는 필터에서 잡지 않는다 (Nest 기본 처리기 → 500 + 로그).
- 클라이언트 응답에는 내부 정보(테이블, 쿼리)를 넣지 않는다.

## 근거
- 클라이언트가 일으킬 수 있는 에러는 4xx, 500은 진짜 서버 문제에만 남긴다.
- `PrismaClientValidationError`를 400으로 바꾸는 안은 반대했다.
  대부분 "검증하지 않은 입력을 Prisma까지 보냈다"는 **서버 쪽 버그 신호**라, 400으로 바꾸면 버그가 숨는다.
- P2003 → 409: "자식이 있는 부모 삭제"와 "없는 부모 참조" 두 상황을 모두 설명할 수 있다.

## 결과
- P2003 → 409는 **안전망**이다. 예상할 수 있는 경우는 서비스에서 먼저 확인해 정확한 코드를 준다
  (예: 없는 게시글에 댓글 작성 → 서비스에서 404).
- 삭제된 사용자의 토큰으로 글 작성 시 현재 409. 본래는 Guard에서 401이 맞다 → [0007](0007-anonymize-users-on-withdrawal.md)
