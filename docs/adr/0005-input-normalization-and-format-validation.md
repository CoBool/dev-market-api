# 0005. 입력값 정규화와 형식 검증

- 상태: 승인됨
- 날짜: 2026-10-08

## 배경
원본 API는 "정상적인 입력"만 가정했다. 직접 확인한 결과:
`/articles/1.5` → 1번 글, `/articles/3000000000` → 500, 검색어 `%`·`_` → 전체 목록,
` 판다 ` → 0건(`판다`는 10건), `REACT` → 0건(`react`는 1건), 대소문자만 다른 이메일로 중복 가입 가능.

## 결정

### 정규화 (DTO의 `@Transform`, 검증보다 먼저 실행)
| 입력 | 처리 | 공용 함수 |
|---|---|---|
| 이메일 (가입·로그인 모두) | trim + 소문자 | `common/transforms/normalize-email.ts` |
| 검색어, 게시글 제목·본문, 댓글 내용 | trim | `common/transforms/trim.ts` |

- trim 후 빈 문자열인 제목·본문·댓글은 `@IsNotEmpty()`로 400.
- `@IsString()`은 항상 함께 둔다 (`@IsNotEmpty()`는 타입을 확인하지 않는다).

### 검색
- LIKE 특수문자 `\`, `%`, `_`는 **서비스**에서 이스케이프한다 (DB 문법이므로 DB 바로 앞에서).
- 대소문자 구분 없음 (`mode: 'insensitive'`).
- 공백만 있는 검색어 → 검색 안 함 → **전체 목록**.

### 경로 id
- `IdParamDto`: 정규식 `^[1-9]\d*$`를 통과한 문자열만 숫자로 바꾸고, `@Max(2147483647)`(PostgreSQL integer).
- 그 외(`0`, `-5`, `01`, `0x10`, `1e3`, `1.0`, 앞 공백)는 400.

## 근거
- 앞뒤 공백은 모바일 자동완성·복사로 **사용자도 모르게** 들어간다. 거절(400)하는 대신 지운다.
  Stack Overflow·GitHub API도 검색어 앞뒤 공백을 무시한다.
- 공백만 있는 검색어: Stack Overflow·Hacker News는 전체 결과, GitHub는 422. 게시판은 검색창을 비우면
  원래 목록으로 돌아가는 게 자연스러워 전체 목록을 택했다.
- `Number()`는 `0x10`, `1e3`, `1.0`, 앞 공백도 숫자로 바꾸므로 `@Type(() => Number)`만으로는 부족하다.
  `ParseIntPipe` 뒤에 검사를 붙이는 방식은 전역 `ValidationPipe({ transform: true })`가 먼저 숫자로 바꿔
  원래 문자열을 볼 수 없다.

## 결과
- 쿼리 파라미터(`page`, `limit`)는 `?page=1e1`(→10) 같은 표기를 그대로 받는다. 해가 없어 허용한다.
- 기존 DB의 이메일이 정규화되지 않았다면 로그인이 안 될 수 있다 (2026-10-08 기준 개발 DB는 모두 정규화됨).
