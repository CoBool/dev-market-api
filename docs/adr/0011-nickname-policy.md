# 0011. 닉네임 정책

- 상태: 승인됨
- 날짜: 2026-10-09

## 배경
닉네임 규칙은 `@IsString()` + `@Length(1, 20)`뿐이었다. 직접 확인한 결과:
`"   "`(공백만)으로 가입 가능, `" 판다"`와 `"판다"`가 서로 다른 값이라 unique를 통과했다.
화면에서는 똑같이 보이므로 **사칭**에 쓸 수 있다.

## 결정
닉네임 하나가 식별과 표시를 모두 맡는 방식을 유지하고, 규칙을 다음과 같이 정한다 (`SignUpDto.nickname`).

```ts
@Transform(trim)                     // 1. 앞뒤 공백 제거
@IsString()
@Length(2, 10)                       // 2. trim 후 2~10자
@Matches(/^[가-힣a-zA-Z0-9]+$/)      // 3. 한글 완성형, 영문, 숫자만
nickname: string;
```

| 입력 | 결과 |
|---|---|
| `판다`, `CoBool99`, `판다Pa1` | 허용 |
| `"  판다  "` | `판다`로 저장 |
| `판`(1자), 11자 이상 | 400 |
| `판 다`, `판다!`, `판다_1`, `판다😀`, `ㅋㅋㅋ`, `"   "` | 400 |
| 이미 있는 `판다`에 `" 판다 "` | 409 |

### 중복 응답
- 회원가입 시 서비스(`AuthService.signUp`)에서 **이메일 → 닉네임** 순서로 `findUnique`해 409를 준다.
  메시지로 어느 필드가 중복인지 구분한다: `이미 사용 중인 이메일입니다.` / `이미 사용 중인 닉네임입니다.`
- 둘 다 중복이면 이메일 메시지가 나온다.
- DB unique 제약과 P2002 → 409(`이미 사용중인 값입니다.`, [0004](0004-prisma-error-mapping-and-logging.md))는
  동시 가입 같은 경쟁 상황의 안전망으로 남긴다.

## 근거
- 서비스는 크게 **고유 ID + 표시 이름 분리**(GitHub, X, Discord)와 **닉네임 하나**(국내 커뮤니티·중고거래 대부분)로 나뉜다.
  스키마가 이미 `nickname @unique`인 후자이고, 이 방식은 닉네임 규칙을 엄격하게 두는 것이 일반적이다.
- 금지 목록이 아니라 **허용 목록** 방식이라 공백, 특수문자, 이모지, 보이지 않는 문자가 한 번에 막힌다.
- 한글을 `가-힣`(완성형)으로 잡아 자음·모음 단독(`ㅋㅋㅋ`)도 함께 막힌다.
- 앞뒤 공백은 거절하지 않고 지운다 ([0005](0005-input-normalization-and-format-validation.md)와 같은 이유).
- `@Length`와 `@Matches`를 하나의 정규식(`{2,10}`)으로 합치지 않는다. 나눠 두면 어느 규칙에 걸렸는지
  에러 메시지로 구분된다 (`password`와 같은 방식).
- 공백만 있는 닉네임은 trim 후 `""`가 되어 `@Length(2, 10)`에 걸리므로 `@IsNotEmpty()`를 따로 두지 않는다.
- DB 컬럼 `VarChar(20)`은 그대로 둔다. 제한은 DTO가 더 엄격하므로 문제없고, 규칙이 바뀔 때마다
  마이그레이션할 필요가 없다.
- 중복 필드 구분:
  - P2002의 `meta`에서 필드를 읽는 안은 버렸다. Prisma 7 + adapter에서는
    `meta.driverAdapterError.cause.constraint.index`(`"User_email_key"`)처럼 어댑터 내부 구조에 있고,
    예전 버전의 `meta.target`과 모양이 달라 업데이트 때 조용히 깨질 수 있다 (직접 확인).
  - 조회를 `findFirst` + `OR` 한 번으로 합치지 않는다. 이메일과 닉네임이 **서로 다른 사용자**의 것이면
    행이 2개인데 `findFirst`는 하나만 돌려줘 어느 메시지가 나올지 정해지지 않는다.
    `findUnique` 두 번이면 우선순위가 코드 순서로 보이고, unique가 아닌 필드는 컴파일 에러가 난다.
  - 추가 쿼리(unique 인덱스, 1ms 이하)는 바로 뒤의 bcrypt 해시(수십 ms)와 가입 요청 제한(IP당 1분 3회)에 비해 작다.
  - 이메일 중복을 알려 주면 가입 여부가 드러나지만, 대부분의 서비스가 가입 화면에서 알려 주고
    (이미 가입한 사용자를 로그인으로 안내), 가입 요청 제한이 대량 확인을 막는다. 닉네임은 원래 공개 값이다.

## 결과
- 보류한 것:
  - **영문 대소문자 무시 중복** (`Panda`/`panda` 공존 가능). 표기를 지키면서 중복만 막으려면
    `lower(nickname)` unique 인덱스가 필요하고, Prisma 스키마로 표현할 수 없어 마이그레이션 SQL을 직접 써야 한다.
    다음 단계에서 따로 다룬다.
  - **예약어** (`admin`, `관리자`, `운영자` 등). 관리자 기능이 생길 때 정한다.
- 알려진 한계: 조합형(NFD) 한글(macOS 파일명 등에서 복사한 값)은 `가-힣`에 걸리지 않아 400이 된다.
  막히는 쪽이라 보안 문제는 아니며, 필요해지면 trim에 `normalize('NFC')`를 더한다.
- 규칙은 **가입할 때만** 검사한다. 기존 데이터에는 소급하지 않으며, 규칙에 맞지 않는 기존 닉네임도 로그인은 된다
  (2026-10-09 개발 DB는 `migrate reset`으로 비웠다).
- 닉네임 변경 API를 만들면 같은 규칙을 써야 한다. 그때 공용 데코레이터로 뺀다.
- DB에는 CHECK 제약이 없어, API를 거치지 않는 경로(seed, 직접 SQL)는 규칙을 지키도록 직접 신경 써야 한다.
- 가입 화면이 이메일 가입 여부를 알려 주므로, 로그인 응답 시간으로 가입 여부가 드러나는 문제
  (없는 이메일이면 bcrypt 비교를 건너뜀)는 우선순위가 낮아졌다.
- 관련 테스트: `test/auth.e2e-spec.ts`의 nickname 케이스와 중복 409 케이스.
